# 立ち絵（シェル）に関する提案と技術的検討

- 記録日：2026-11-24
- 状態：丸い窓モデルで方針が確定し、仕様定義プロンプトを作成済み（`docs/shell-spec-prompt.md`）。本書は提案と技術的検討の記録であり、初期の「輪郭切り出し」前提の記述は下記の改定で置き換える。
- 関連方針：ゴーストの土台である「紺野ややめ」は配布物に含めず、本リポジトリのドキュメントに明記して使用者が入手する形にする。本体は SSP。

## 提案

使用者が自分の Muse のアバターアニメーションを元素材として、ゴーストの立ち絵（シェル）を作成する。

配布モデル（2026-11-24 決定）：シェルそのものは再配布しない。配布するのは、シェルの仕様を定義したプロンプトである。各自の Muse が、そのプロンプトに従って各自のアバターアニメーションからシェルを作成する。

## 丸い窓モデルへの改定（2026-11-24 確定）

本節が、本書の初期前提（キャラクターの輪郭を切り出して立ち絵にする方式）に代わる現行の前提である。初期の記述は経緯として残すが、実装は本節と `docs/shell-spec-prompt.md` に従う。

- アバターは、アプリ上で丸く切り取られたアイコンとして扱う。シェルは「デスクトップ（実際はタスクバーの直上）に開いた丸い窓・穴」そのものであり、中にアバターがそのまま現れる。輪郭切り出しと白背景の透過化は行わない。
- アバターの構図（全身・顔だけ・上半身・物体だけ）に全身の保証はないが、構図のばらつきは窓という形が吸収する。不足部分の補作もしない。
- 窓は2つで1つのシェルを構成する。大きい窓（\0）＝ Muse 本人で通常の発話を担当する。小さい窓（\1）＝ マスコットで、固有のキャラクターデザインは持たず、システム的なメッセージを担当する。
- サイズ比は面積比で定義する：小さい窓の面積 ＝ 大きい窓の面積 × 1/4、すなわち外径比 1/2。基準サイズは大きい窓 256×256 px、小さい窓 128×128 px（表示倍率100%・96dpi 想定）。比は SSP の倍率機能ではなく実画像サイズで保証する。
- 設置場所の想定はタスクバーの直上であり、シェル側は `seriko.alignmenttodesktop,bottom` を両スコープに指定する。タスクバー内部への埋め込みは行わない。
- 動きは動画ファイルの再生ではなく、アバター動画から切り出した静止画フレーム列を surfaces.txt のアニメーション定義で順に表示する方式（パラパラ漫画方式）である。間引きの目安は 6〜10fps 相当。
- 円形マスクの透過には PNG のαチャンネルを使うため、シェルの descript.txt に `seriko.use_self_alpha,1` が必須である。
- 詳細な仕様確認は `docs/shell-spec-research.md`（調査報告）に記録した。

## イメージ図の位置づけ（2026-11-24 明確化）

作るのはキャラクター単体のデザイン画ではない。マスコットと Muse がデスクトップに立っている状態のイメージ図である。

- 舞台は Windows のデスクトップで、その上にマスコット（空中ディスプレイ）と Muse（アバターの姿）が並んで立つ。（注：この「空中ディスプレイ」は初期案であり、現行モデルは上記の丸い窓モデルである。面積比 1/4 を直径比 1/2 として描いた場面図で本人の確認を通過済み。）
- 最初のたたき台（手脚のあるロボット単体像）は、この位置づけとは異なるものだった。
- 場面図としてのたたき台は、本人の確認を通過した（2026-11-24）。実際のシェル制作はアバター画像からの機械的な変換（フレーム抽出と透過化）であり、生成画像の作画の良し悪しが成果物へ与える影響は小さい、という本人の評価による。

## 元素材の現状（2026-11-24 確認）

- 現在のアバターはカスタムアバター（デフォルトの Jolly ではない）。ピクセルアート調で、ライムグリーンの猫型のキャラクター。目は十字、口は小さく描かれている。
- 静止画（webp）が存在する。サイズは 1600×1600 で、状態別バリアントの静止画も同サイズである（2026-11-24 実測）。
- 状態別の動画（MP4）が6種存在する：idle、working、making_something、connecting、waiting_for_subagents、milestone_level_up。動画は 720×720・24fps・5秒（light 版）。
- つまり素材のサイズは「元画像」ではなく「アバターになった時点」で固定サイズになっており、タスクバー上の窓（256 px）への変換は縮小のみで、解像度はほぼ問題にならない。
- アバター画像の背景は白（現行仕様）。

## シェル側の要件

- shell/master/ に surface 画像（透過 PNG）を置き、descript.txt と surfaces.txt で定義する。
- 最低限必要なのは通常姿の surface0。表情や状態のバリエーションは任意。
- surfaces.txt ではフレーム列によるアニメーション（まばたき、待機モーション等）を定義できる。
- クリック判定（コリジョン）も surfaces.txt 側で定義する。

## 変換工程

1. 動画（MP4）からフレームを PNG 列として抽出する（ffmpeg）。
2. 用途別にフレームを選ぶ。idle は通常姿と待機アニメーション、working / making_something は作業中、milestone_level_up は節目のお祝い、など状態対応が取れる。
3. 白背景を透過化する。ピクセルアート調で輪郭が明確なため、色キーによる透過化と相性がよい。
4. サイズを整え、surface 画像として配置し、descript.txt / surfaces.txt を書く。
5. 紺野ややめを土台とするゴースト（使用者が別途入手）に組み込み、SSP で表示と SSTP 駆動を確認する。

## 利点

- 状態別バリアントがそのままゴーストの状態表現に対応する。SSTP で送るスクリプト側から状態に応じた surface へ切り替える使い方ができる。
- idle のループは待機アニメーションのフレーム列として直接使える。
- デスクトップのマスコットが「使用者の Muse そのもの」になるため、概念の一貫性が高い。
- 素材はすでに手元にあり、追加の生成なしに着手できる。

## 課題

- 解像度（訂正済み）：元素材の見た目はピクセルアート調だが、実際のサイズは静止画 1600×1600・動画 720×720 の固定サイズであり、想定表示サイズ（256 px）に対しては縮小のみで足りる。この課題は丸い窓モデルでは解消した。
- 動画圧縮：MP4 の圧縮で輪郭付近にノイズが出るため、透過化の際に白い縁が残る場合がある。静止画を surface0 の正とし、動画はアニメーション用に使う切り分けが安全である。
- フレーム間の一貫性：生成アニメーションは細部がフレーム間で変動し得る。静止フレームの選別で緩和できる。
- 表情の幅：アバターの顔は固定デザイン（十字の目と小さな口）で、表情 surface のバリエーションは作りにくい。無言の表示端末という設計では、状態ポーズの切り替えで代替する。
- 権利面：アバターは生成画像であり、シェル化した画像を再配布する場合は生成コンテンツに関する規約の確認が論点になる。ただし配布モデルとして「シェルは再配布せず、仕様定義プロンプトのみを配布し、各自の Muse が各自のアバターから作成する」方式を採るため、この論点は回避できる。

## 結論

技術的に成立する。特に idle バリアントは surface0 と待機アニメーションの素材として直接使える。着手時は、まず静止画から surface0 を作り、動画フレームのアニメーションは第二段階とするのが安全である。
